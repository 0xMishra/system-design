A URL shortener is a web service that converts long, complex URLs into shorter, more manageable links that redirect users to their original destination.

For example, consider a long URL:

`https://example.com/products/electronics/smartphones/iphone-17-pro?campaign=summer-sale` 

A URL shortener converts it into something like:

`https://short.ly/aB92xK` 

When a user clicks the shortened URL, the service identifies the corresponding original URL and redirects the user to it.



### **Why do we need a URL shortener?**
Long URLs can be difficult to share, remember, and manage, especially across platforms with character limitations, such as social media, SMS, and messaging applications.

URL shorteners solve this problem by providing:

- **Compact links:** Make lengthy URLs easier to share.
- **Redirection:** Automatically redirect users to the original destination.
- **Analytics:** Track metrics such as the number of clicks, geographic locations, and referral sources.
- **Link management:** Allow users to create, manage, and potentially customize their shortened URLs.


### **How does it work at a high level?**
1. A user submits a long URL to the URL shortener service.
2. The service generates a unique short identifier (e.g., `aB92xK` ).
3. It stores the mapping between the short identifier and the original URL in a database.
4. When someone accesses the shortened URL, the service retrieves the original URL using the identifier.
5. The service redirects the user to the original destination, typically using an HTTP redirect (301 or 302).

### Functional requirements 
Let's gather some functional requirements for our url shortener service.



1. **URL creation:** 
User will submit a long URL file `https://example.com/very-long-url`  and the system has to create a corresponding short url mapped to this long url like `https://tiny.url/a2b3e5K` 



2.  **URL direction:**
When the user tries to access the tiny url generated by the system, the system must redirect the user to the corresponding original long url mapped to this one.

`https://tiny.url/a2b3e5K`  -> `https://example.com/very-long-url` 



### Non functional requirements 


1. **Low latency:**
Response time for each request  should be as low as feasible.



2.  **High availability** 
Availability is the measure of how often a system is operational and accessible to users when they need it. So our system should have high availability.



### Clarifying questions 
We have to clarify some questions before moving further.



How many URLs will be created per second?

Let's assume we have to create around 1000 URLs per second.

This means we will have around 1000 writes per second to our database.

For an entire year this will be:

1000 X 60 X 60 X 24 X 365 ~ 31.5B URLs created per year. This means we will have around 31.5B writes per year to our database.

If we assume that the reads will be 10X of this then that will around 315B database reads per year



What characters can we use for our tiny URL path?

We should restrict to alphanumeric characters for our tiny URL path which means A-Z, a-z and 0-9, that will be a total of 62 characters.



What will happen if multiple users submit the same long URL to the system?

In this case should we map it to the same tiny url for each user or should we create a new short url for each person. Let's create a new tiny URL for each user.



### Data estimation
So far we have decided that our system should have 

- 1000 URLs per second
- Alphanumeric characters 
- New tiny URL for the same long URL when different users submit same long URL.


But how long should our URL be? Ideally we should have a balance between short URLs but also not running out of possible combinations of characters.



Let's calculate number of unique URLs required per year. A common approach in system design is to plan for few years ahead, for this one lets assume a period of 10 years.

Seconds in 1 year: 60 X 60 X 24 X 365 ~ 31.5M

Seconds in 10 years: 10 X 31.5M = 315M

Total URLs in 10 years:  1000 X 315M = 315B



Length of URL Identifier:

62^1 = 62 Unique URLs ( 1 character)

62^2 = 3844 Unique URLs ( 2 characters)

.....

62^6 = 56B Unique URLs ( 6 character)

62^7 = 3.5T Unique URLs ( 7 characters)

So our URL identifier should be 7 characters long



Data storage:

Short URL Identifier: 7 Bytes

Long URL: 100 Bytes

User metadata: 500 Bytes

Total ~1000 Bytes



For 10 years the estimated storage would be 1000 X 315B = 315 Terabytes of data.

### API design
We will have two endpoints for our REST API.

- POST api/urls:
Input:

JSON payload with the long url:

```
{{"long_url":"https://example.com/very-long-url"}} 
```
Output:

```
{"short_url":"https://tiny.url/a2b4aK7"}}

200 Created 
400 Bad Request
409 Conflict (Optional)
```
Well return 409 if the requested URL already exists in the system but that is optional and depends if we allow duplicate short URLs for same long URLs



- GET api/urls/{shortUrlId}
Input: short URL Id path parameter [abc123]

Output:

```
301 Moved permanently (or 302)
404 Not found
410 Gone
```
301 status code indicates that the redirection is permanent and this tells the browser to cache this information that the short URL has moved to the long URL. So next time user types the same short URL in the browser the browser uses it own cache to redirect the user to the mapped long URL without even hitting our server.



If you want monitoring and get analytics you should use 302 status code.

410 if the URL has expired.





### Database design
Our database stores the mapping between the short and long URLs and should be optimized for faster reads and writes.

If we assume our system gets 1000 writes per second then it will get somewhere around 10k to 100k reads per second. Hence we need a fast and high-performance database so a NoSQL database like mongo DB or Cassandra DB would be the optimal choice here.

Schema of our database:

```
{
  "shortUrlId":"a1b2c3F",
  "longUrl":"https://example.com/very-long-url",
  "creationDate":"2026-04-06T12:00:00Z",
  "userId":"user123",
  "clicks":6408,
  "metadata":{},
  "isActive":true
}
```


It won't be ACID compliant but we don't need to worry about it because we are not gonna do a lot of complex queries and table joins.



### URL shortener service 
This is the main component of our system we need to make sure this service is able to generate short URLs without any collisions meaning mapping different long URLs to the same URLs.

- We can use hashing but it can lead to collisions.
- We can auto increment IDs ensures uniqueness but might be predictable


To avoid this we can make our own custom method like generating all the possible keys with 7 alphanumeric characters and store them in a database with a boolean value representing whether they have been used or not. We don't need to store entire short URL because it will be the same for all IDs.

```
{
  "a1b2b3d":true,
  "g1j2a5L":false
}
```
What kind of database should be used to store the keys. Suppose two user submit a long URL and both get mapped to same ID to avoid this we will use an SQL database because it comes with ACID properties. We can create transactions in isolation to avoid this.



### High availability and low latency
To ensure these two qualities in our system we will us a cache to get quicker access to popular URLs without a DB lookup. But redis has limited space so we need an eviction policy to prioritize frequently accessed URLs.

- LRU ( remove least recently accessed items first)
- TTL ( fixed time to live for each cache entry)

### Database scaling
Considering we have 3.5T URLs we need a database we can use key based sharding to distribute URL records across multiple shards evenly 



We can also implement master-slave replication for each shard, for each shard we will have 1 master DB and 3 slave DB. Since we will be getting a lot more reads than writes we can use 3 slave DBs only for reads and 1 shard as master DB for reads and writes.

### Security considerations 
To make sure our system is secured against all plausible vulnerabilities we have to implement few security measures like.

- Input validation: To have input validation in our API to avoid attacks like SQL injection and avoid processing malicious links server will run a background check before storing it.
- Rate limiting:  To avoid DDOs attacks using algorithms like token bucket 
- HTTPS: ensure all communications are encrypted to protect user data.
- Monitoring and logging system with tools like Elasticsearch, Logstash, Kibana
